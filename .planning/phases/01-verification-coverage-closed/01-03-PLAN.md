  <decision>How should `newton_kl` be treated under KPI-02's unconditional weight-bound assertion?</decision>
  <context>
Measured during planning, reproduced on three independent seeds, and identical in BOTH
`bounds_mode="unit"` and `bounds_mode="cell"`:

    harvest(..., method="newton_kl", min_weight=0.2, max_weight=5, bounds_mode="unit")
      -> returned min(w) = 0.0051, max(w) = 296.9      (seed 7)
      -> returned min(w) = 0.0009, max(w) = 740.9      (seed 11)
      -> returned min(w) = 0.0063, max(w) =  64.7      (seed 23)
      -> n_bounds_clamped = 0 in every case; the water-fill never ran.

The other eight solvers all returned exactly `min(w) = 0.2` and `max(w) = 5` on the same
fixture, with the clamp counter in the hundreds.

This is not obviously a bug. `tests/testthat/test-newton-bounds-write-guard.R` documents a
deliberate, shipped contract for this solver (leafblower-73d7, referred to as "T4"): when
more than five percent of weights violate the bounds, `newton_kl` sets status to
`RK_ERR_NOCONV`, surfaces `n_bounds_violated > 0`, and refuses to write the violating vector
to `best_weights`. It REPORTS violations rather than clamping them. The planning runs
returned exactly that non-OK status, so the documented contract is firing as designed.

So KPI-02's literal wording ("`max(w) <= max_weight` and `min(w) >= min_weight` within
1e-10") and `newton_kl`'s shipped contract genuinely conflict. Existing coverage hides the
conflict: `test-clamp-contract.R` sweeps five solvers and does not include `newton_kl`, and
on an easy uniform fixture `newton_kl` returns all weights equal to 1, trivially inside any
bounds.

This phase is test-layer only by its own boundary — no solver, binding, or `src/` change
lands here — so either option below is a test-and-ticket outcome, not a solver fix.
  </context>
