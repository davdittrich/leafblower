<objective>
Give the package a Windows build path. It ships a Unix-only `configure` that generates
`src/lbw_config.h`, `.Rbuildignore` excludes that header from the tarball, and there is no
Windows counterpart — so every Windows R build fails at the first `#include "lbw_config.h"`.
This is confirmed live: all 5 Windows configs on r-universe's check farm FAIL to compile
(build 32069801748), and 05-RESEARCH.md's assumption A5 that "CRAN win-builder has its own
fallback" is empirically disproved.

Purpose: CRAN checks Windows by default, so Phase 7 cannot submit until this compiles. The
project has no Windows development machine, so this plan buys a real Windows oracle
(a windows-latest GitHub Actions runner) rather than reasoning about a platform it cannot
observe — and it buys it BEFORE the fix, so the failure is reproduced here rather than taken
on faith from someone else's log.
Output: a Windows check job in this repository's CI, a `configure.win`, and a green Windows
`R CMD check --as-cran`.
</objective>

  </read_first>
  <action>
    Add a `configure.win` at the repository root, mode 755, written in POSIX `sh` (R runs it
    through the shell Rtools provides). It must do exactly the two things the Unix `configure`
    does, and nothing more:

    1. Write `src/lbw_config.h` with the same three macros and the same include guard as the
       Unix script emits, with `LBW_HAS_GLIBC_MVEC` set to 0 and both OpenMP macros set to 0.
       Do NOT port the three feature probes. Their outcome is already determined on this
       platform: glibc's vector math library is Linux-only, so the AVX2 path must be compiled
       out; and the two OpenMP macros are read by no source file, so probing for them would
       add Windows-specific failure modes while producing no information. Put that reasoning
       in a comment at the top of the file so the next reader does not "restore" the probes.
    2. Substitute `src/Makevars.in` into `src/Makevars.win` using the same `sed` invocation
       shape as the Unix script, with: the C++ standard placeholder set to the C++17 flag; the
       SIMD placeholder set to the OpenMP-simd-only flag (accepted by every Rtools GCC since
       4.9 and by the LLVM-based aarch64 toolchain, and requiring no runtime library); and the
       OpenMP, AVX2 and vector-math-library placeholders all emptied.

    Leave `src/Makevars.in` untouched. This is load-bearing: because the OpenMP placeholder is
    emptied rather than filled, the compiler emits no calls into an OpenMP runtime, and
    `PKG_LIBS` therefore needs no runtime entry. On Windows an unresolved symbol at link time
    is a hard error rather than a deferred one, so enabling threading here would require a
    matching `PKG_LIBS` change on BOTH platforms; there is no threading to enable, so do not
    open that door.

    Add `Makevars.win` to `src/.gitignore` beside the existing entries — it is generated, like
    its Unix sibling. Do not add `configure.win` to `.Rbuildignore`: it MUST ship in the
    tarball or it cannot run on the user's machine, which is the entire defect.

    Verify what can honestly be verified locally, and be explicit in the SUMMARY about the
    boundary: locally you can prove the script is valid POSIX shell, that it runs, that the
    header it writes is well-formed C with the three macros defined, and that the Makevars it
    writes has every placeholder substituted; you CANNOT prove locally that Rtools' compiler
    accepts the flags or that the package links on Windows. Run the local checks in a scratch
    copy of the tree so the repository's own generated `src/lbw_config.h` is not left holding
    Windows values, then push and let the windows-latest job from Task 1 be the oracle.
  </action>
