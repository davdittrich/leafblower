<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| GitHub Actions OIDC → PyPI upload authority | A short-lived OIDC token minted in CI is exchanged for permission to publish under the project name; anything that can run that job can publish |
| Third-party GitHub Action → CI runner with id-token: write | `pypa/gh-action-pypi-publish` executes inside a job holding upload authority |
| Published artifacts → every downstream `pip install leafblower` user | Whatever this job uploads is executed on end-user machines at install/import time |
| Git tag push → release trigger | Any pushable tag matching `refs/tags/*` triggers a publish attempt |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-13 | Elevation of Privilege | Long-lived `PYPI_API_TOKEN` repository secret | high | mitigate | Not used at all — OIDC Trusted Publishing (D-09/D-10) means no upload credential is ever stored in the repo, its secrets, or a developer machine |
| T-05-14 | Tampering | `pypa/gh-action-pypi-publish` supply chain (floating tag could be re-pointed) | high | mitigate | Pinned to commit `dc37677b2e1c63e2034f94d8a5b11f265b73ba33` (v1.14.2), matching this repo's existing SHA-pinning convention; org identity `pypa` verified via `gh api orgs/pypa` at research time |
| T-05-15 | Elevation of Privilege | `id-token: write` granted too broadly, letting an unrelated job mint an upload token | high | mitigate | The permission is declared at job level on `publish-to-pypi` only, never workflow-wide, and that job is additionally gated on `startsWith(github.ref, 'refs/tags/')` and the `pypi` environment |
| T-05-16 | Spoofing | Name-squatting or typo-squat of `leafblower` on PyPI before first publish | medium | mitigate | The pending-publisher registration (Task 2) reserves the exact project name at PyPI before any upload exists; Task 3 verifies the served files come from the claimed project |
| T-05-17 | Tampering | An accidental or malicious tag push triggering an unintended release | medium | accept | Sole repo owner, tag-gated trigger plus a `pypi` environment that can later take a required-reviewer rule; adding a protection rule now is discretionary per D-11 and not proportionate today |
| T-05-18 | Repudiation | Uploaded artifacts not traceable to the commit that produced them | low | accept | The publish runs only from a tagged commit in this repo and PyPI records the Trusted Publishing provenance (workflow, repo, environment) for each file |
</threat_model>
